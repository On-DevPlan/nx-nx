## 0. 读到的上下文（先读懂再动手）

- 仓库 `nx-nx` 是**通用模板生成器**：`templates/<id>/` 下每套模板满足同一契约
  （`template.json` + `files/` + 可选 `hooks.mjs`），由 `src/core/templates.ts` 发现与校验。
- 现有 5 套模板目录：`server-cli-web`（JS）、`server-cli-web-ts`（TS）、`mono-gf`（Go）、
  `std-a-lang`（目录骨架）、`ui-kit`（**无 template.json → 属于坏模板，列表里报错**）。
- `server-cli-web` 与 `server-cli-web-ts` 是同一骨架的两个语言版本（前者 `.js`、后者 `.ts`），
  TS 版额外带一套类型系统（`runtime/types/{action,module,client,http}.ts`）。
- 任务 #1（scripthub 方案评价）已落 `plan/2026-11-09-scripthub-方案评价.md`；本次沿用其体例：
  **结论先行 + 逐条对照 + 证据 + 分级建议**。

## 2. Phase B —— 验证「zod + 装饰器」模型（spike，不进模板）

**为什么先做 spike 而不是直接改模板**：任务明说「先验证这个模型」。把未经批准的模型塞进
已发布的 TS 模板，违反「保留既有功能」的底线；spike 在仓库内自洽验证，结论再决定是否下沉。

spike 位置：`spike/zod-decorator/`（仓库根，独立于 `templates/` 与 `src/`，不参与发版产物）。

要验证的四个断言（来自任务原文）：

1. **CLI 完全自动化** —— 树、help、参数解析、派发全部从声明派生，零手写 switch。
2. **前端 apiclient 半自动化** —— codegen 能生成到哪一步、剩下的必须手写什么，要能量化。
3. **注解方式** —— TC39 标准装饰器在 Node 22 + tsx + TS 5.9 下是否可用、代价是什么。
4. **只维护保留 ts 版本** —— 该模型是否**要求** TS（若是，则 JS 版天然出局，删除即无损失）。

spike 产物：

```
spike/zod-decorator/
├── src/action.ts      装饰器 + 元数据收集
├── src/schema.ts      zod schema ↔ CLI flag 规格 / CLI 输入归一化
├── src/registry.ts    类 → actions → 校验
├── src/tree.ts        CLI 树构建 + help
├── src/cli.ts         树驱动的 CLI（解析 + 派发）
├── src/codegen.ts     生成 cli-tree.json + 前端 client 源码
├── src/demo/module.ts 用装饰器声明的示例模块（含 zod input/output schema）
├── generated/         生成物（cli-tree.json / client.generated.ts）
└── test.mjs           断言：树完整、client 与 action 对账、zod 拦截、CLI 归一化语义
```
