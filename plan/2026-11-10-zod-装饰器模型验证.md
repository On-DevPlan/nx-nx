# zod + 装饰器 action 模型验证（任务 #2 第二问）

> 任务原文：「其次测试 zod 加装饰器到 action 上，同时生成树的 cli 和给前端使用的 apiclient。
> 你先验证一下这个模型：cli 完全自动化 / 给前端调用的后端 apiclient 半自动化 / 注解方式 /
> 只维护保留 ts 版本」
>
> 验证方式：**写一个能跑的 spike**（`spike/zod-decorator/`，29 条断言 + tsc + eslint 全绿），
> 用可执行的证据回答四条断言，而不是纸上推演。
> 环境：Node v22.23.2 · pnpm 12.11.2 · TS 5.9 · zod 4.6.7 · tsx 4.23.15（esbuild）。
>
> 姊妹文档：任务 #1 的 scripthub 评价（`plan/2026-11-09-scripthub-方案评价.md`）——
> 同一套体例：结论先行 + 逐条对照 + 证据 + 分级建议。

## 0. 结论先行

**模型成立，但成立的方式和直觉相反。**

- 「CLI 完全自动化」成立：命令树、help、参数解析、派发全部从声明派生，CLI 里没有一个字面量命令名。
- 「apiclient 半自动化」成立，而且「半」可以量化：**每条 action 的调用代码手写量 = 0 行**；
  手写的是**每个项目一次**的传输层（45 行）与**页面里用到哪个 action 就写哪一段**的交互接线
  （约 10 行/action）——两者都**不随 action 数量增长**。
- 「注解方式」可用，但**要付两笔代价**：handler 的入参类型必须手写 `z.output<typeof schema>`；
  编译期检查（路由参数与 args 的一致性）**降级为运行期检查**。
- 「只维护保留 ts 版本」成立且比任务预期更强：模型的核心收益（schema → 类型）**只在 TS 存在**。

但真正值得报告的不是「成立」，而是**这个模型解决的不是任务想解决的那个问题**：
zod + 装饰器把「输入契约」做成了单一真相源（服务端校验 / 前端表单校验 / codegen 类型来源三处共用），
代价是**输出契约要显式声明**（装饰器拿不到 handler 的返回值类型），于是每条 action 从「写一个函数」
变成「写两个 schema + 一个函数」。§5 给出「该不该下沉到模板」的判断。

## 1. 模型长什么样（spike 的实际形状）

对比对象是仓库现有模型：`runtime/types/action.ts` 的 `defineAction({...})(run, render)` 两段式 builder。

```ts
// 现有（builder）：字面量 → 编译器推出 ctx 类型 / run 返回值类型
defineAction({
  id: 'home.greet', cli: ['greet'], http: ['POST', '/api/greet'],
  args: [{ name: 'name', required: true }], flags: { loud: { type: 'boolean' } },
})((ctx) => greet(ctx.name, !!ctx.loud), (r) => r.greeting);

// spike（注解 + zod）：schema 是真相源，装饰器挂元数据
@action({
  id: 'demo.greet', cli: ['greet'], http: ['POST', '/api/greet'],
  args: ['name'], input: demoGreetInput, output: demoGreetOutput,
})
greet(ctx: z.output<typeof demoGreetInput>) { ... }
```

spike 的 6 条 action（实际跑出来的形状，`*` = 必填，`(pos)` = 位置参数）：

| action | CLI | HTTP | schema 字段 |
| --- | --- | --- | --- |
| `demo.greet` | `greet` | `POST /api/greet` | `name:string*(pos), loud:boolean` |
| `demo.echo` | `echo` | `POST /api/echo` | `text:string*(pos), repeat:number, tags:array, mode:enum` |
| `demo.config` | `config set` | `PATCH /api/config` | `set:kv, payload:json, dry-run:boolean` |
| `demo.ping` | `ping` | `GET /api/ping` | （无） |
| `demo.stats` | `stats` | `GET /api/stats` | `days:number` |
| `demo.item` | `item get` | `GET /api/items/:id` | `id:string*(pos)` |

三条实现选择，都是实测逼出来的（详见 `spike/zod-decorator/src/action.ts` 头注释）：

| 选择 | 理由 | 实测 |
| --- | --- | --- |
| 元数据挂**方法函数**（WeakMap），不用 `context.metadata` | `Symbol.metadata` 在 Node 22.23 是 undefined；tsx 会给 `context.metadata` 传对象，但 tsc 编译后交给原生 Node 就是 undefined → 元数据静默丢失 | 断言 `typeof Symbol.metadata === 'undefined'` 仍能收集到全部元数据 |
| 装饰器**不改方法签名** | TC39 标准装饰器要求返回类型与原方法兼容 | handler 入参类型只能手写 `z.output<typeof schema>` |
| 每条 action 同时声明 **input + output** 两个 schema | 装饰器拿不到 handler 返回值类型 | 输出类型只能靠 output schema 显式声明——这是「半自动化」的根源之一 |

## 2. 四条断言逐条对照

| 断言 | 结论 | 证据（可复现） |
| --- | --- | --- |
| **CLI 完全自动化** | ✅ 成立 | ① 命令树由声明构建（`src/tree.ts`），help 由树渲染；② 派发走树的最长匹配，CLI 里**没有 switch、没有命令表**；③ 测试断言 `src/cli.ts` 源码里**不出现任何命令名字面量**（把 `greet`/`echo`/`stats`… 逐个查）——这条断言让「自动化」可证伪；④ `generated/cli-tree.json` 与注册表逐条对账（id 集合相等） |
| **apiclient 半自动化** | ✅ 成立，「半」可量化 | 自动部分：每个 action 一个方法、名字、入参/返回类型、路由模式、路径参数抽取、query/body 分流、入参出参各一次 zod 校验。手写部分：**传输层 45 行/项目**（base url / 鉴权 / 错误信封 / 超时，只写一次）、**页面接线约 10 行 / 页面里用到的每个 action**（按钮 → action → loading/失败态）。两者都**不随 action 数量增长**；spike 6 条 action 的 client 生成物 86 行，其中每条 action 约 8 行、全部为机器产出 |
| **注解方式** | ⚠️ 可用，有两笔代价 | 可用：TS 5.9 + Node 22 + tsx 下标准装饰器正常工作，装饰器守卫（只标方法）有断言。代价一：handler 入参类型要手写 `z.output<typeof schema>`（现有模型是 `CtxOf<S>` 自动推导）。代价二：路由 `:param` 与 args 的一致性检查从**编译期红**降级为**运行期红** |
| **只维护保留 TS 版** | ✅ 成立，且比预期强 | 模型的核心收益是「schema → 类型」：`z.input` / `z.output` 让前端 client 与 handler 共享同一份类型事实。JS 版拿不到这些类型，只能退回手写类型或不要类型——**JS 版在这个模型下没有存在形态**。任务 #2 第一问（删 JS 模板）因此不是「顺手删」，而是被这个模型直接证成 |

## 3. 四个必须记住的坑（都已写进代码注释并被断言钉住）

### 坑 1：`z.coerce` 不能直接用

```ts
z.coerce.boolean()('false')  // → true   ← 静默反转语义
z.coerce.number()('')`       // → 0      ← 笔误变成另一个合法值
```

既有模型（`runtime/spec.ts` 的 `coerceOne`）专门处理过这两点：布尔认 `false/0/no/''`，
裸 flag（`--port` 后面没跟值）一律报错而不是当成 1。spike 复刻了这两条语义
（断言：`--loud=false` → false；`--repeat` 裸 flag → 报错「需要提供值」）。
**结论：zod 替代的是「校验」，替代不了「归一化」——归一化层必须自己写。**

### 坑 2：HTTP 的 query 参数也是字符串

「HTTP 是原生类型」只对 **body** 成立。`?days=3` 拿到的是 `"3"`，`?loud=false` 拿到的是 `"false"`。
于是同一份 schema 在 HTTP 侧也要过归一化（spike 里 CLI 与 HTTP 共用同一个归一化函数，
端到端断言 `GET /api/stats?days=3` → `days === 3`）。**「一份 schema 两端用」成立，
但「一份 schema 不用适配」不成立。**

### 坑 3：装饰器元数据不能挂在 `context.metadata` 上

tsx（esbuild）会给 `context.metadata` 传一个对象，看上去能用；但 `Symbol.metadata`
在 Node 22.23 里是 undefined，**一旦用 tsc 编译后交给原生 Node，这个对象就是 undefined，
元数据静默丢失**。挂方法函数（WeakMap）与运行时无关，最稳。

### 坑 4：`z.input` 与 `z.output` 不能混用

`.default()` 让字段在 **input 侧可选、output 侧必填**。handler 拿到的是**解析后**的值 → 用
`z.output`；前端 client 的入参是调用方提供的 → 用 `z.input`。spike 里最初把 handler 写成
`z.input`，tsc 立刻报 `ctx.repeat` 可能是 undefined——**类型系统把这个混用抓出来了**，
这正是「只留 TS 版」这条断言的正面证据。

## 4. 与现有模型的逐项对照（同一个东西，两种写法）

| 维度 | 现有 builder 模型 | spike：zod + 装饰器 |
| --- | --- | --- |
| 入参真相源 | `flags` / `args` 字面量 | zod schema（可复用到前端） |
| ctx 类型 | `CtxOf<S>` 自动推导（编译期） | 手写 `z.output<typeof schema>`（编译期，但靠人写对） |
| 返回类型 | `RunResult<A>` 自动推导 | 必须显式声明 output schema |
| 输入校验 | `spec.ts` 手写强转 + 校验 | zod（规则写在 schema 里） |
| CLI flag 类型 | `FlagSpec.type` 手写 | 从 schema 反推（**依赖 zod 内部 `_zod.def.type`，版本敏感**） |
| 路由/args 一致性 | 编译期红（`ParamsCovered`） | 运行期红 |
| 前端 client | 类型由注册表推出，运行时靠 `/api/bootstrap` 下发路由 | codegen 出实体文件；类型来自 schema |
| 前端表单校验 | 无（前端不知道服务端约束） | **同一份 schema 直接复用**（zod 浏览器安全） |
| 每条 action 的手写量 | 一个字面量 + 一个函数 | **两个 schema + 一个函数**（多了 output schema） |
| 可重复 flag（kv） | `type: 'kv'` + 解析器收数组 | zod 无对应概念，仍需归一化层处理 `k=v` 重复 |

## 5. 判断：该不该下沉到 `server-cli-web-ts` 模板

**建议：分两步，不要一次全量下沉。**

### 第一步（建议做，价值最高、风险最低）：只加 zod，不换声明形态

在 TS 模板里引入 zod，**保持 `defineAction` 的 builder 形态**，把 `flags`/`args` 换成 zod schema：

- 收益：输入契约单一真相源；服务端校验与前端表单校验共用；`z.input`/`z.output` 直接产出类型。
- 代价：现有 `spec.ts` 的归一化逻辑（boolean/kv/json/array 的 CLI 语义）要保留并与 zod 对齐——
  **zod 替不掉归一化**（坑 1、坑 2）。
- 风险可控：现有类型系统（`CtxOf`/`ValidateAction`/`ParamsCovered`）一行不动，
  zod 只是给 flags 加了一层更严的运行时校验 + 可选的类型来源。

### 第二步（建议暂缓）：换注解形态 + codegen 前端 client

理由是它换来的东西**不足以抵消换掉的编译期保证**：

- 注解形态丢掉的：ctx 类型自动推导、路由/args 的编译期检查；
- 注解形态换来的：声明与实现写在一起（类聚合）、装饰器可读性；
- codegen 前端 client 换来的：实体文件（可提交可 diff）、schema 与前端同源；
  代价：多一套生成物与「生成物过期」的维护面（现有模型是运行时派生，无过期问题）。

**如果要做，注解形态应当是可选的第三种写法，而不是替换 builder**——
即 `defineAction` 保留，新增 `@action` 作为 sugar，共用同一套 registry / spec / client 类型层。

### 明确不建议

- **不建议把 zod 的类型来源建立在 `_zod.def.type` 这类内部 API 上**（spike 用了，
  因为它必须回答「这个字段在 CLI 上是 number 还是 string」）——
  zod 换版本可能改内部结构。若要下沉，应改用 `.meta()` 或自定义包装类型显式标注 CLI 形态。
- **不建议现在就给 output schema 加硬要求**（spike 的做法）：每条 action 多写一个 schema 是
  真实成本，除非前端 client 真的要用到返回类型，否则收益不抵成本。
  折中：output schema 可选，声明了才给 client 生成返回类型。

## 6. 落地清单（若采纳第一步）

1. TS 模板 `package.json` 加 `zod` 依赖；`src/runtime/types/action.ts` 增 `zod` 版 action 形状。
2. `src/runtime/spec.ts`：现有 `coerceOne` 保留为「归一化层」，新增 zod 解析作为「校验层」，
   两者串联（归一化 → 校验）。
3. `src/runtime/types/client.ts`：入参类型从 `z.input` 出，返回类型从 `z.output` 出（声明了 output schema 才有）。
4. 前端：`src/web/frontend/api/` 增加「用同一份 schema 做表单校验」的一条通路（zod 是浏览器安全的，
   但要确认 schema 模块不 import node:* —— 与现有 eslint「前端禁 node 内置」规则天然对齐）。
5. 闸门：`tests/unit/` 增加「每个 action 的 schema 与 flags 声明一致」的用例；
   现有 `flags` 形态与 zod 形态二选一（不要长期并存两套真相源）。

## 8. 复审修正记录

spike 交给 code-reviewer 过了一遍，发现的问题都已修掉并补了回归断言（这本身也是模型
「验证」的一部分——**一个没人用的能力（例如别名）不该留在验证用的 spike 里**）：

| 问题 | 修正 |
| --- | --- |
| handler 被当自由函数调用，`this` 是 undefined → 类无法持有状态 | 改为在实例上调用（`method.call(instance, …)`），demo 改用实例字段计数 |
| `aliases` 声明了、查重了、却派发不了（树节点没挂 action） | 别名节点挂 `aliasOf`，派发认它、help 不重复列；补别名用例 |
| 位置参数按 **schema 字段顺序**消费，而文档说按 `args` 顺序 | `describeInput` 按 `args` 下标重排；补「args 顺序与 schema 顺序故意不同」的用例 |
| `context.metadata` / `Symbol.metadata` 的依赖写在注释里，断言也依赖运行时版本 | 断言改为检查**实现源码**（注释行剔除后不含这两个名字），Node 将来补上 `Symbol.metadata` 也不会让测试变红 |
| spike 没有闸门，CI 不会发现它烂掉 | `test:spike` 与 `typecheck:spike` 进 `pnpm test` |
| 死代码：`export { z }`、`ModuleDef.title` 只写不读、前端文件没人引用 | 删掉 / 把模块标题写进 tree 快照 / 把前端层接进端到端用例 |
